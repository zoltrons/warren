# Passkeys and inline menu: comparison with six shipped extensions (2026-11-12)

Static reading of the Chrome Web Store packages in `~/Downloads/research`: 1Password 8.12.44, Bitwarden 2026.10.2
(source maps), Dashlane 6.2646.1, NordPass 7.12.16, Proton Pass 1.43.0, iCloud Passwords 3.4.0. These are idea
references only (see CLAUDE.md): nothing below copies their code. Nothing was run. Claims about other extensions come
from their manifests and code. Claims about Warren come from `src/`. The spec column follows WebAuthn L3
(w3.org/TR/webauthn-3), MDN Passkeys, passkeys.dev, Google's passkey guides and FIDO. A **(verify)** mark means the
behaviour was inferred, not reproduced.

Priority: **P1** breaks a common flow, **P2** loses interop or a feature that sites use, **P3** hardening or polish.

## Passkeys

| # | Area | What others do | Correct approach | Warren today | Weakness | Fix | P |
|---|---|---|---|---|---|---|---|
| P-1 | Fallback to the browser after our window | Bitwarden waits for `top` focus (`waitForFocus`, up to 5 min) before calling the native API. 1Password focuses a field first (Safari) | Chrome rejects create/get from an unfocused document (NotAllowedError) | `settle()` calls the native `create/get` as soon as the relay answers `fallback`, while the approval window is still closing | "Use another device / browser" and closing the window can end in NotAllowedError instead of the browser dialog **(verify)** | Before the native call in `passkey-page.ts`, wait for `document.hasFocus()` (`focus` event, bounded) | P1 |
| P-2 | RP ID outside the origin (Related Origin Requests) | 1Password reports `relatedOrigins: true`. Bitwarden calls `isValidRpId` (`domain-utils.ts`) | rpId that is not the host or a registrable parent: fetch `https://<rpId>/.well-known/webauthn` and check `origins` (at least 5 labels), otherwise SecurityError | `checkRpId` throws only once the worker runs. A get then shows "no passkeys" (candidates `.catch(() => [])`). A create fails with NotAllowedError after the user clicks | Sites that rely on ROR (amazon.*, regional domains) cannot register or sign in, and the browser never gets the call | In `handle()`, check the RP ID before opening anything: invalid means `{fallback: true}`. Optionally add ROR (SW fetch, 5-label limit, short cache) | P1 |
| P-3 | Conditional create (automatic passkey upgrade) | 1Password reports `conditionalCreate: false`. None of the six implement it | `mediation: "conditional"` on create: create silently (UP=0, UV=0) only if this provider just signed the user in with a password for that account and origin. Otherwise NotAllowedError | The relay needs `userActivation.isActive` for create, so the call goes to the browser | With Google Password Manager on, Chrome may save the upgraded passkey there, not in the vault | In `handle()`: conditional create is accepted when Warren filled a password for this origin and username in the last few minutes (`markUsed` / the fill path). Save into that login and show a notification. Report `conditionalCreate: true` | P2 |
| P-4 | `getClientCapabilities()` | 1Password and Dashlane override it (conditionalGet, hybrid, passkeyPlatformAuthenticator, uvpa, relatedOrigins, `extension:credProps`, `extension:prf`) | Map of capability to true/false, keys sorted. Modern sites read it before offering passkeys | Only `isUserVerifyingPlatformAuthenticatorAvailable` / `isConditionalMediationAvailable` are patched | On a browser without a platform authenticator (Linux, some Helium setups), sites see `passkeyPlatformAuthenticator: false` and hide passkey creation and autofill | Wrap the native result and set `conditionalGet`, `passkeyPlatformAuthenticator`, `userVerifyingPlatformAuthenticator`, `extension:credProps` to true. Claim nothing Warren does not do (`relatedOrigins` only after P-2, `conditionalCreate` only after P-3) | P2 |
| P-5 | Signal API | 1Password lists all three as `false`. None implement them | `signalUnknownCredential` hides or removes the credential. `signalAllAcceptedCredentials` hides the ones missing from the list. `signalCurrentUserDetails` updates name and displayName. All are page-callable: hide rather than delete | Calls reach the browser only | Passkeys deleted on the site stay in the vault. A renamed account keeps its old name | `signalCurrentUserDetails`: update `userName`/`userDisplayName` for a matching rpId + userHandle (no data loss). The other two: never delete. Mark the passkey "site no longer accepts it" in the item view and let the user remove it | P2 |
| P-6 | UV when `userVerification: "preferred"` | Bitwarden treats preferred like required: it shows a PIN, biometric or master password dialog unless the vault was just unlocked. The platform managers always verify | Preferred: verify if the authenticator can. Many RPs give a UV=1 passkey a full sign-in, and UV=0 only a second factor | UV=1 only after an unlock or master password typed for this request. The window verifies with the master password only (`ui/passkey.ts`) | In an unlocked vault, preferred yields UV=0, so some sites ask for more. Required forces typing the master password | Allow biometric unlock (`ui/biometric.ts`) and the PIN as UV in the approval window. For preferred, offer one touch when biometrics are set up. Invariant 11a still holds | P2 |
| P-7 | Sign counter | Bitwarden increments and saves when the stored counter is greater than 0 (imported passkeys). It stays at 0 otherwise | A non-zero counter must increase. RPs may flag a clone | `assert` signs with the stored counter and never raises it | A passkey imported from another manager with counter > 0 repeats the same value. Strict RPs refuse it | If counter > 0: +1 and save the item (ciphertext through the worker, like passkeyCreate) before answering | P2 |
| P-8 | `user.id` and option quirks | Bitwarden: TypeError outside 1–64 bytes. `requireResidentKey: "true"` string quirk. Timeouts clamped (2 min, 5 min with UV) | user.id is 1–64 bytes (TypeError) | `capped(1024)` characters. An empty id passes | An empty or too-long id is stored. Discoverable sign-in then returns no or a wrong userHandle | Check 1–64 decoded bytes in `parsePasskeyCall` and answer TypeError | P2 |
| P-9 | AAGUID | Bitwarden uses its own AAGUID (`d548826e-79b4-db40-a3d8-11116f7e8349`) | With `none` attestation a zero AAGUID is allowed. RPs map AAGUID to a provider name and icon in passkey lists | All zeros | Sites list the passkey as "unknown" | Decided (2026-11-12): use Bitwarden's AAGUID; the credential lives in a Bitwarden vault and the official apps serve it too | P3 |
| P-10 | PRF extension | Proton, 1Password and NordPass return `prf` results. Bitwarden's extension does not | `prf.enabled` on create, `prf.results.first/second` on get. The output must be stable on every device that holds the passkey | Not supported | Sites that encrypt data with PRF cannot use Warren passkeys for that | Not planned (decided 2026-11-12). It needs a per-credential secret, and Bitwarden's `fido2Credentials` schema has no field for it. Official apps would compute different output, and data encrypted with it would be lost. Listed under the gaps in PARITY_REPORT.md | — |
| P-11 | Calls from iframes | Bitwarden now accepts frames whose permissions policy allows `publickey-credentials-get/create` (`webauthn-permissions-policy.background.ts`) | crossOrigin = !sameOriginWithAncestors. `topOrigin` when cross-origin. Permissions policy decides. Cross-origin create needs activation | Top frame only (`frameId !== 0` disconnects, the shim is top-frame) | Passkeys in embedded sign-in or checkout frames go to the browser | Inject in all frames. In the relay (isolated world, not spoofable), check `document.featurePolicy.allowsFeature(...)`. Pass crossOrigin/topOrigin from `sender` and put them in clientDataJSON | P3 |
| P-12 | Prerendered pages | 1Password waits for `prerenderingchange` | No UI until the page is shown | A conditional request from a prerendered page registers at once | Inline-menu passkey entry and TTL start for a page the user has not seen | When `document.prerendering`, wait for `prerenderingchange` before `ask()` | P3 |
| P-13 | Hook robustness | 1Password: `Object.defineProperty`, non-configurable getter/setter. Dashlane: `Proxy` on the original | — | Plain assignment `c.create = …` | A page script or another manager overwrites it, and Warren silently stops answering | Define with `defineProperty` (keep it configurable if a fallback needs it) | P3 |
| P-14 | Shim ↔ relay channel | Bitwarden: `MessageChannel`, a private port per request. 1Password: syn/ack with random ids | — | `window.postMessage(…, "*")` both ways (accepted in SECURITY.md) | Other extensions' content scripts can read assertions on the window bus | A `MessageChannel` port per call, sent with the request | P3 |
| P-15 | Conditional UI next to the browser's | 1Password does not call the native API in conditional mode when it serves the request. Bitwarden races like Warren | — | Races the native conditional UI and adds an inline-menu row | Chrome's dropdown and Warren's menu can both open under the field **(verify)** | Keep the race (it keeps hardware keys and phones working). Open Warren's menu above or below the field depending on space (I-4) so they do not cover each other | P3 |

## Inline menu

| # | Area | What others do | Correct approach | Warren today | Weakness | Fix | P |
|---|---|---|---|---|---|---|---|
| I-1 | Modal `<dialog>`, popovers, fullscreen (top layer) | All except Bitwarden-on-Firefox use `popover="manual"` + `showPopover()`. Bitwarden places it inside an open `:modal` dialog and re-raises when another top-layer item appears (with a hijack limit). Dashlane hooks `showModal`/`showPopover` | Top-layer content is above everything, and its position is not affected by ancestor transform/filter | `<warren-menu>` appended to `<html>` with z-index 2147483647 | Inside `dialog.showModal()` the menu is under the dialog and inert (no clicks). Popovers cover it. `transform`/`filter` on `<html>` (dark-mode extensions) breaks `position: fixed` | Host gets `popover="manual"` and calls `showPopover()` after append. If the field is inside an open `:modal` dialog, append the host to that dialog. Call `showPopover()` again on each `place()` when `:modal, :popover-open` exists (bounded) | P1 |
| I-2 | Focus-trapping ARIA modals | Bitwarden appends inside `[role=dialog][aria-modal=true]` | — | Appended outside the modal | Focus traps pull focus back from the menu frame. ArrowDown → menu breaks, and clicks may too **(verify)** | Same container rule as I-1 (closest `dialog:modal` or `[aria-modal=true]`) | P1 |
| I-3 | Fields in small or cross-origin iframes | NordPass, Dashlane and iCloud use `chrome.runtime.getFrameId(iframe)` to position the menu from the top frame. Bitwarden collects sub-frame offsets and draws in frame 0 | The menu is drawn where it fits: the top document | Drawn inside the field's own frame | Stripe, Adyen and Braintree card fields are single-field iframes about 40 px high. The menu is cut off, and the IO-v2 guard then refuses clicks. Card inline fill on checkouts mostly does not work | Draw in frame 0. The field frame reports its rect. Each parent adds its iframe's offset (border, padding) by matching `e.source` to `iframe.contentWindow` (no new permission), or uses `chrome.runtime.getFrameId`. Keep the nonce and fill targeting `ctx.frameId` | P1 |
| I-4 | Placement | Proton, NordPass and 1Password use `ResizeObserver` and `IntersectionObserver` on the field | Flip above when there is no room below. Clamp to the viewport. Follow layout shifts | Always below. Left clamp uses a fixed 324 px while width goes up to 420. Moves only on scroll/resize | Near the bottom, the menu is off screen. Wide fields at the right edge overflow by up to 96 px. A layout shift (error text, banner) leaves it detached | Use the real width in the clamp. Put it above when `r.bottom + h > innerHeight`. Add a `ResizeObserver` on the anchor and `<html>` that calls `place()` | P2 |
| I-5 | Card and identity fill across frames | Chrome autofill fills same-origin frames, and cross-origin ones where `shared-autofill` allows it | One pick fills the whole form, even when split over frames | `inlineFill` form mode fills only `ctx.frameId`. `fillInFrames` refuses frames on another origin | Split card forms (number, expiry, CVC each in an iframe) get one field | For form mode, fill all frames of the tab whose origin equals the triggering frame's. Cross-origin payment frames follow Chrome's `shared-autofill` rule **(verify the rule first)** | P2 |
| I-6 | Closed shadow roots | 1Password, Dashlane and NordPass call `chrome.dom.openOrClosedShadowRoot` | — | `deepAll`, `active()` and `field-watcher` see open roots only | Fields in closed web components (some banks, design systems) get no menu or fill | Use `chrome.dom.openOrClosedShadowRoot(el)` in the collector walk, the focus lookup and the watcher | P3 |
| I-7 | Clickjacking and visibility | Bitwarden: `elementFromPoint` obscured check, page-opacity check, top-layer hijack counter. Others: `checkVisibility` | — | IntersectionObserver v2 `trackVisibility` + 300 ms per frame, nonce, closed shadow root, trusted-gesture focus | Stronger than the others already. With top layer (I-1) a page can still stack its own popover over Warren's | Keep it. After I-1, the IO-v2 guard still covers stacking, so no new code is needed | — |
| I-8 | Host removed or restyled by the page | Bitwarden watches the container's last child and z-index with a MutationObserver | — | No watch | A page that clears `<body>`/`<html>` children (SPA re-render) leaves `anchor` set with no menu until the next focus | Before acting, check `host.isConnected` in `place()` and in the passkey refresh path, and `close()` when false | P3 |

   dialog login and a focus-trap modal.
